# SignalDesk Commit 09 - CDP Tool Layer

Commit 09 creates deterministic, typed Python tools before introducing an
agent. It separates two responsibilities:

```text
model responsibility, added in Commit 10
  choose whether and how to call a tool

application responsibility, implemented here
  validate arguments, execute bounded data access, validate output,
  report explicit errors, and prevent side effects
```

No model chooses tools in this commit. No tool writes to the CDP, contacts a
customer, persists a recommendation, or executes an intervention.

## Tool contracts

| Tool | Reads | Boundary |
|---|---|---|
| `get_customer_profile` | `customer_360` | PII-safe profile only |
| `get_customer_events` | `stg_events` | Identity-resolved, 1-90 days, at most 100 events |
| `get_purchase_history` | orders, items, products | 1-730 days, at most 50 orders |
| `search_knowledge_base` | generated knowledge corpus | Current-approved lexical baseline, at most 10 documents |
| `calculate_customer_metrics` | `customer_360` | Existing deterministic metrics; no new score |
| `get_campaign_eligibility` | profile, consent, campaign recency | `BLOCKED` or `REVIEW_REQUIRED`; never claims final eligibility |
| `create_retention_recommendation` | profile and policy authority metadata | Non-persisted draft; execution always disabled |

Each tool has:

```text
name
description
strict Pydantic input schema
strict Pydantic output schema
bounded query behavior
structured error contract
side_effects = none
```

The definitions are generated by `ToolRegistry.definitions()`. Commit 10 can
show these contracts to a model without giving the model database access.

## Data-access boundaries

### Customer profile

The profile tool returns customer status, loyalty tier, geography, semantic
as-of time, recency, and identity count. It does not expose raw email address,
phone number, postal address, birth date, or identity values.

### Event history

Event lookup uses `resolved_customer_id`, so it follows the deterministic
identity resolution built in Commit 03. The lookback window is relative to the
Customer 360 `as_of_ts`, not the machine clock. Results are ordered by event
time and bounded by an explicit limit.

### Purchase history

Purchase lookup returns orders with product-line evidence. It preserves order
status, including canceled and refunded orders, instead of silently treating
every order as successful revenue.

### Metrics

The metrics tool groups existing Customer 360 features into purchase,
engagement, support, campaign, and subscription/consent domains. It does not
invent a composite engagement score, churn probability, or causal effect.

### Knowledge search

Commit 09 uses a local deterministic lexical adapter restricted to current,
approved documents. The output names the method as
`lexical_current_approved`.

This adapter is a tool-contract baseline, not a reversal of the Commit 08
vector-retrieval decision. A vector adapter can later implement the same tool
contract, but it must earn adoption through retrieval and tool-level
evaluation. Keeping the interface separate from the search implementation is
the API-design lesson.

### Campaign readiness

The warehouse does not contain enough information to prove final campaign or
offer eligibility. A specific campaign definition, audience rule, current
policy interpretation, and offer terms are not supplied to this tool.

The tool therefore returns only:

```text
BLOCKED
REVIEW_REQUIRED
```

It never returns `ELIGIBLE`. Customer status and channel consent create hard
blocks. A contactable channel permits review, not execution.

### Recommendation draft

The caller supplies a recommendation type, rationale, Customer 360 evidence
feature names, and policy document IDs. Application code attaches the actual
feature values and verifies that every document is current and approved.

The deterministic output states:

```text
status                  = DRAFT
requires_human_approval = true
execution_allowed       = false
persisted               = false
```

The draft ID is a hash of the complete request and semantic as-of time. The same
inputs produce the same ID. Verifying policy authority does not prove that a
policy semantically supports the rationale, so that limitation remains in the
output.

## Error contract

The registry converts failures into stable codes:

| Code | Meaning |
|---|---|
| `VALIDATION_ERROR` | Arguments violate the typed contract |
| `NOT_FOUND` | Customer or authoritative policy document does not exist |
| `CONFLICT` | A valid request conflicts with a hard business boundary |
| `UNKNOWN_TOOL` | Tool name is not registered |
| `INTERNAL_ERROR` | Execution failed without exposing internal details |

SQL values are parameterized. Extra arguments are rejected. A malformed ID,
unknown event type, excessive lookback, invalid channel, unknown policy ID, and
attempted action-like recommendation all have measured behavior.

## Frozen evaluation

`evals/commit09/cases.jsonl` contains 105 cases:

```text
7 tools
10 valid cases per tool   = 70
5 invalid cases per tool  = 35
5 measured repetitions    = 525 executions
```

The benchmark warms each case once before measuring. Latency includes input
validation, execution, output validation, and result-envelope construction. It
does not include one-time DuckDB connection or lexical-index construction.

## Reproduce

```bash
python -m pip install -r requirements-commit09.txt
python -m evals.commit09.make_cases

python -m coverage erase
python -m coverage run \
  --branch \
  --source=src/tools \
  -m unittest tests.commit09.test_tools
python -m coverage json -o evals/commit09/reports/coverage.json

python -m evals.commit09.benchmark
python -m unittest discover -s tests -v
```

## Definition of done

Commit 09 is complete when:

- all seven tools have strict input and output contracts,
- all data access is bounded and read-only,
- PII remains outside model-facing profile output,
- recommendation creation remains draft-only and non-persisted,
- every tool has valid and invalid frozen cases,
- valid-call and invalid-input behavior are measured,
- p95 latency is measured per tool,
- test coverage is above 80%,
- the learning log and Blog 09 contain measured conclusions,
- no agent loop or automatic action is introduced.
